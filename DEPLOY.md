# Deploying studentबंधु

This app is one Node process (`server.js`) with zero npm dependencies — it serves the
HTML/CSS/JS itself and stores users in `data/users.json`. That makes a persistent
Node host the simplest deploy: no serverless rewrite, no database migration.

## Recommended: Render (free/cheap, simplest)

1. Push this folder to a GitHub repo.
2. On Render: **New → Web Service** → connect the repo.
3. Build command: (leave empty — there's nothing to build)
4. Start command: `node server.js`
5. Add environment variables (Render → your service → Environment):
   - `ANTHROPIC_API_KEY` — required for any AI feature to work
   - `ADMIN_EMAILS` — comma-separated emails that can see `/admin-dashboard`
   - `NODE_ENV=production`
6. Add a **persistent disk** mounted at `/opt/render/project/src/data` (Render's disk
   add-on) so `data/users.json` survives restarts/redeploys. Without this, registered
   users are lost on every redeploy — the app still works, it just starts empty each time.

Railway and Fly.io work the same way (`node server.js` as the start command, a
persistent volume for `/data`). Any of these is a fine choice — Render is just the
one with the simplest free tier for a project this size.

## Why not Netlify (as configured here)

The `_redirects` file and the `studentbandhu-netlify.zip` bundle in this project
assume Netlify's static hosting, which cannot run `server.js` as a long-lived process
or keep in-memory sessions/rate-limits. Getting a real backend on Netlify means
rewriting every `/api/*` route in `server.js` as an individual serverless Function and
swapping the in-memory session/rate-limit Maps and the JSON file store for something
that survives across invocations (e.g. Netlify Blobs or a real database). That's a
different, larger project — happy to do it if you'd rather go that route, but it's not
what's in this build. `_redirects` is otherwise harmless to leave in place; `server.js`
already serves the same clean URLs (`/login`, `/sign-in`, etc.) itself.

## What changed in this pass

- **AI provider**: switched from OpenAI to Claude (Anthropic Messages API).
  Set `ANTHROPIC_API_KEY` (see `.env.example`).
- **Removed the fake demo mode**: `app.js` used to detect "not running on localhost"
  and silently switch to a browser-only, `localStorage`-based fake backend. That's
  gone — the app always talks to the real server now, and shows a clear error if it
  can't reach it.
- **Dashboard is now fully real**: knowledge score, weekly study time, concepts
  mastered, the progress chart, exam readiness, the knowledge map, root-cause
  insight, recent activity, and streak are all computed from real per-student data
  the server already tracked — none of it was wired to the UI before.
- **Syllabus → concept map**: registration now asks Claude to break the course/
  syllabus into real units and concepts (falls back to a simple default if no API
  key is set), seeding the diagnostic instead of only discovering concepts ad hoc.
- **Root-cause insight**: a real AI call, but only fed real, already-computed
  numbers (weak concept, accuracy, related concepts) — it explains them, it
  doesn't invent them, and it's cached until the weak concept actually changes.
- **Practice and lessons are AI-generated now**: both used to be a fixed set of
  generic recursion questions/a canned lesson, unrelated to the student's actual
  subject. Both are now generated by Claude for the student's real weakest concept,
  and both are answer-validated server-side (previously `/api/practice/answer`
  trusted a client-supplied `correct: true/false` with no server check at all).
- **Admin dashboard is real**: it had no backend, no login gate, and fully static
  numbers. It now requires a session + `ADMIN_EMAILS` match, and every figure is
  computed live from `data/users.json`.
- **Fixed a real CSS/JS bug**: the dashboard had two separate, conflicting
  "scroll story" implementations (duplicate chart tooltips with different fake
  data, and a CSS rule that could hide the real chapter nav on mobile). The
  duplicate was removed.
